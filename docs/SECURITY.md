# SECURITY

- **Trust domains:** parent JWT vs device JWT; `role` claim enforced on every function; device tokens can't reach parent endpoints.
- **Secrets:** service-role key, device JWT secret, FCM service account, pairing pepper live only in Edge Function secrets. Never in web bundle, BuildConfig, git, logs.
- **Enrollment:** 80-bit random single-use pairing code (typed or QR), stored only as `HMAC-SHA256(pepper, code)`, TTL 10 min, consumed atomically, one live code per child; unknown/expired/used codes fail identically; per-IP attempt limit is defence in depth on top of 2^80 guessing space (see Phase 8 controls).
- **Device auth:** 15-min access JWT; refresh token rotation with reuse detection (family revoke); revocation = immediate (checked via `device_credentials.revoked_at`).
- **Commands:** nonce + expiry + status machine; FCM is signal-only, authorization comes from authenticated fetch.
- **Transport/Storage:** HTTPS only, `cleartextTrafficPermitted=false`, Keystore-wrapped tokens, no plaintext SharedPreferences.
- **Data access:** RLS everywhere, least-privilege functions, audit logs for sensitive reads (e.g. LOCATION_VIEWED).
- **Logging:** no coordinates, contacts, tokens, identifiers in logs/crash/analytics/URLs.
- **Testing:** IDOR, RLS bypass, JWT tampering, replay, brute force, SQLi/XSS/CSRF, cross-family — Phase 31/33.
- **Non-goals (prohibited):** stealth, keylogging, credential capture, root/exploits, hidden recording, anti-uninstall malware, privacy-indicator circumvention.
- **Phase 2 controls:** CORS exact-origin allow-list; JSON body ≤64 KB with content-type check; validation errors never echo submitted values; unhandled errors log only error name; device JWT HS256 alg-pinned with constant-time verify; `check:secrets` blocks server secret names in `apps/web`.
- **Phase 4 controls:** parent access via RLS only (`owns_*` helpers, column-level grants, ownership columns immutable); FCM tokens, credential hashes and pairing tokens have no parent policy/grant; parent-created commands are PENDING-only with ≤24 h expiry; audit logs read-only for parents; `anon` has zero access; a device-JWT `sub` matches no family so it sees nothing through parent RLS. Verified by `05_rls.test.sql` (cross-family read/write/delete, IDOR, column tampering, forged history, anon/no-sub/device principals).
- **Phase 5 controls (parent auth):**
  - *Sessions:* Supabase Auth cookies are `HttpOnly; SameSite=Lax; Secure` (prod) and set only by the Next server (middleware / Server Actions / `/auth/confirm`); the browser never handles tokens. Every request revalidates with `auth.getUser()` (never trusts `getSession()`), refresh-token rotation on, cookie writes carry `Cache-Control: no-store`. Trade-off: browser-side Realtime cannot read the token — decided in Phase 6: data flows through Server Components/Actions (RLS under the parent's JWT) and interval `router.refresh()`; a browser token is a separately reviewed decision (see ARCHITECTURE §8).
  - *Sign-up/login:* Zod on the server (password 12–72 chars, upper/lower/digit/symbol, mirrors `config.toml`); email confirmation required (enforced by GoTrue, by middleware `emailConfirmed`, and by the `(app)` layout); login/sign-up/reset/resend answers are identical for existing vs unknown accounts (no user enumeration); provider errors are mapped to generic messages, never echoed; passwords never returned to the client or logged.
  - *Reset/confirm links:* `/auth/confirm` accepts only `signup|email|recovery|email_change`, token charset-checked, `next` restricted to same-origin relative paths (open-redirect tests); all failures redirect identically. Password change revokes all other sessions (`signOut({scope:"others"})`).
  - *MFA (TOTP, optional):* enrol/verify/unenrol via Server Actions; users with a verified factor are held at `/mfa` (aal1→aal2) for every protected route including password reset; challenge attempts throttled per user.
  - *Rate limiting:* per-IP and per-account limits on login, sign-up, reset, resend, MFA (in-memory per instance — shared store in Phase 31) on top of GoTrue limits.
  - *Headers:* per-request nonce CSP (`script-src 'self' 'nonce-…' 'strict-dynamic'`, no `unsafe-eval` in prod, `frame-ancestors 'none'`, `object-src 'none'`, `connect-src` limited to self + the Supabase origin), HSTS (prod), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` (camera/mic/geolocation off), COOP; auth pages `no-store`. CSRF: Server Actions are POST-only with Next's Origin/Host check; logout is a POST form.
  - *Parent JWT on Edge Functions:* `requireParent()` — device tokens → 403 before any network call; role must be `authenticated` (anon/service keys rejected); `exp` pre-check; verification by the Auth server (`getUser`, catches revoked sessions); `sub` must equal the verified user; verifier outages surface as sanitized 500, never as "valid"; optional `requireAal2`.
  - *Audit:* `LOGIN` rows (method only — no email/UA/token) are written by the `auth-events` Edge Function with the service role after parent-JWT verification and IP + per-parent rate limits; the browser never calls it. Best-effort: an audit failure never blocks login (it is logged by error name only). The IP is taken from `x-forwarded-for` as forwarded by the web server — a parent could forge only their *own* audit IP; treat as informational until Phase 31 adds a signed server-to-server channel.
  - *Guards:* `check:secrets` keeps server-only secret names out of `apps/web` (source and built output verified).
- **Phase 6 controls (dashboard shell):** no data access in the shell (guarded by `lib/pages.test.ts`: no Supabase/fetch/env in shell files); `(app)` layout still re-verifies the session per render; `[id]` route params must be UUIDs (else 404) and ids are never displayed; the error boundary never renders `error.message` (opaque digest only); theme is an allow-listed HttpOnly cookie set by a Server Action and rendered server-side — no inline scripts, no browser storage, CSP unchanged; no new dependencies added to the supply chain.
- **Phase 7 controls (family/child management):** every mutation is a Server Action → `lib/family/service.ts`: Zod first, verified user via `auth.getUser()`, per-user write rate limit, ownership via RLS with 0-row results treated as not-found (IDOR-safe; foreign ids 404 like missing ones); `parent_id`/`family_id` come from the session/DB, never input; deletes need a `confirm=delete` token from a native-`<dialog>` confirmation that states the cascade (devices + data). Date of birth is personal data: only an age is rendered in lists, it is never placed in URLs/logs/errors (guarded in `lib/pages.test.ts`). Avatars: `avatar_url` validated as https without credentials, but **not rendered or editable** — CSP `img-src` stays `'self' data: blob:`; adding remote avatars later needs an explicit host allow-list plus a CSP change. Initials are shown instead.
- **Phase 8 controls (device enrollment backend):**
  - *Minting:* only through `enrollment-create` (parent JWT, device tokens → 403). Ownership is decided in the database by `enrollment_create_token` (child must belong to `p_parent_id`'s family; foreign ≙ missing ≙ 404). The code is returned once and never stored, logged or echoed in errors; only its HMAC (pepper = Edge secret `PAIRING_TOKEN_PEPPER`) reaches Postgres.
  - *Redeeming:* unauthenticated by design; the `Authorization` header is never read, so parent/device JWTs neither help nor hurt. One `UPDATE … WHERE consumed_at IS NULL AND expires_at > now()` consumes the token inside the same transaction that creates the device, credential and audit row (a failure rolls consumption back; 12 parallel redeems on real PostgreSQL produced exactly one device). Unknown, expired and replayed codes return the same `401` body. Strict request schema: `child_id`, status, ids and FCM tokens cannot be supplied by the device.
  - *Brute force:* the 80-bit space makes guessing infeasible; per-IP limit is 5 attempts/5 min (every attempt counts, so a locked IP is refused even with a correct code). Limiter is in-memory per Edge isolate until Phase 31 (shared store) — do not rely on it as the primary control. Deliberately **no** global limiter (it would let an attacker deny enrollment for everyone).
  - *Credentials:* device JWT HS256 signed with `DEVICE_JWT_SECRET` (15 min, `cid` = credential id, `jti`); refresh token 256-bit opaque, only its SHA-256 stored, unique index enforces one live credential per device. Known gap until Phase 11: an access JWT issued before revocation stays valid ≤ 15 min because `cid` is not yet checked against `revoked_at` on device requests.
  - *Revocation:* `enrollment_revoke_device` (ownership-checked, idempotent, single transaction): status `REVOKED`, all credentials revoked, push token deleted, `DEVICE_REMOVED` audit row. Commands still `PENDING` for a revoked device are not delivered once Phase 20 refuses revoked devices.
  - *Database surface:* the three `enrollment_*` functions are `SECURITY DEFINER`, `search_path=''`, `EXECUTE` for `service_role` only (verified: anon/authenticated/PUBLIC cannot call them). `pairing_tokens`, `device_credentials`, `device_tokens` still have no parent policy or grant.
  - *Privacy:* `DEVICE_ENROLLED` audit rows carry no IP (a child's network address would reveal location that is opt-in elsewhere). Enrollment collects only device name and optional manufacturer/model/OS/app version, and the enrollment dialog tells the parent the app stays visible and the child confirms on the device (no stealth pairing).
  - *Web:* the Next server forwards the parent's own access token (verified by the function); tokens are never stored client-side; logs contain HTTP status only; the dialog keeps the code in component state only and drops it on close; revoke needs a `confirm=revoke` token.
  - *Known limitations:* a lost HTTP response after a successful redeem leaves an enrolled device whose app has no credentials (parent revokes and re-enrolls); FCM token registration is not part of redeem (Phase 10/20); no QR image is rendered yet (typed code only; the QR payload is returned for later).

## Android app foundation (Phase 9)
- Cleartext traffic off (`usesCleartextTraffic=false`, network security config); debug builds may use HTTP only for `10.0.2.2`/`localhost`/`127.0.0.1`. `ApiBaseUrl` enforces the same rule in code and never prints its value; release builds fail unless `-Pfamilysafe.apiBaseUrl` is https.
- `allowBackup=false` and data-extraction rules exclude all app data from cloud backup and device transfer; a restored device must re-enroll.
- Secrets (Phase 10/11 tokens) go through `SecureStore`: AES-256-GCM, fresh random IV per write, key in Android Keystore (non-exportable), record name bound as associated data. Tampered, truncated or moved values read as absent and are deleted.
- Only the launcher activity is exported; R8/shrinking on release; no logging of tokens or identifiers; dependency versions pinned exactly (dependency verification: Phase 31).

## Android enrollment (Phase 10)
- The pairing code is a credential: held only in view state while being typed, cleared on success and whenever it is known or possibly spent, never logged, never persisted, never in `toString` of any type that holds it (tests assert this). No deep link and no camera: the manifest gains nothing (`INTERNET` + `ACCESS_NETWORK_STATE` only), so nothing can pre-fill or auto-submit a code.
- The child confirms on screen before connecting and sees exactly what the parent will receive (device name, manufacturer, model, Android and app version; no serial/IMEI/advertising id). The name is editable.
- `enrollment-redeem` is called with no `Authorization` header and never retried (not idempotent). Failure classification errs toward "may have been spent": a timeout or dropped connection after sending shows the "ask your parent for a new code" path; only failures that provably happen before sending (DNS, refused, TLS handshake, connect timeout) keep the code for retry.
- Credentials (`device_id`, refresh token, expiry) live in `SecureStore` (AES-256-GCM/Keystore). `device_id` is written last and removed first, so a crash mid-write reads as "not enrolled". Storage is probed (write, read, delete) BEFORE the code is redeemed; if the probe fails nothing is sent.
- Redeem runs in an application-lifetime scope so backing out of the screen cannot cancel it after the server consumed the code; the repository still saves the credentials and refreshes app state.
- *Known limitations:* if the response is lost after the server accepted the code, or saving fails afterwards, the device exists in the parent's list without working credentials (parent revokes and re-adds; the app says so). No sign-out/unenroll on the device yet (parent removes it on the website). Unreadable secure storage is treated as "not enrolled" (fail closed; a re-enroll creates a second device row the parent can revoke).

## Device authentication (Phase 11)
- **Two secrets, two lifetimes.** Access token = HS256 JWT signed with `DEVICE_JWT_SECRET`, 15 min, `role=device`, `sub`=device id, `cid`=credential id. Refresh token = 256-bit opaque value, SHA-256 at rest, 30 days sliding, rotated on every use.
- **Revocation is immediate.** `device_authorize` runs on every device request (one indexed lookup, deliberately no cache — a cache would reintroduce a revocation delay). It requires: credential exists for that device, not revoked, not expired, device `ENROLLED`. A credential that was rotated but not revoked still passes, so an access token issued just before a refresh works until its own `exp` (≤ 15 min); revoking (parent or reuse detection) sets `revoked_at` on the whole family.
- **Reuse detection.** Replaying an already-rotated refresh token revokes the family and the device (audited `DEVICE_REMOVED`, `reason: credential_reuse`, no IP, no token material). Trade-off accepted: a legitimately lost refresh response also lands here, so the parent re-adds the device. No grace window — a grace window would let a thief with a copied token keep a second live chain.
- **Uniform failure.** `device-refresh` answers unknown / expired / revoked / replayed / revoked-device identically (401, same body); the database returns only an outcome the Edge Function collapses. Reuse is logged as the constant `device_refresh_reuse` (no ids, no tokens).
- **Concurrency.** Lock order is `devices` → `device_credentials` (same as `enrollment_revoke_device`), so refresh and revoke cannot deadlock; raced on a real PostgreSQL: 12 parallel refreshes of one token → 1 rotated, 1 reused (family revoked), rest invalid, one audit row, zero live credentials; 40 concurrent refresh+revoke pairs → no errors/deadlocks and no live credential on a revoked device.
- **Rate limiting.** 60 attempts / 5 min / IP (in-memory until Phase 31). The token has 256 bits, so this is cost/DoS control, not guess protection; it is deliberately generous because children share carrier-NAT addresses. No per-device limiter after success (it could withhold a response after the DB already rotated).
- **Never** `SELECT`/`EXECUTE` for `anon`/`authenticated` on `device_refresh` / `device_authorize`; both are `SECURITY DEFINER`, `search_path=''`, `service_role` only (pgTAP-verified).
- Known limitations carried forward: no periodic purge of rotated credential rows (Phase 32); refresh expiry slides forever while the device keeps refreshing (absolute session cap is a Phase 31 decision); in-memory limiter per isolate.

## Device authentication on Android (Phase 11b)
- Access token is **memory only**; the refresh token stays in `SecureStore` (AES-GCM/Keystore). Refresh when < 60 s remain.
- **Single-flight:** one `Mutex` guards every refresh, so two callers never present the same refresh token (the server treats that as reuse and revokes the family). A caller cancelled mid-request cannot abort the rotation (`NonCancellable`); otherwise the server would hold a rotated token the device never stored.
- **Persist first, expose second:** if the new refresh token cannot be saved, the new access token is dropped and the device disconnects (`Uncertain`).
- **No blind retries:** only failures that provably happen before rotation keep the stored token (offline, 429, 502/503, other 4xx). A lost or unreadable answer, any other 5xx, a device-id mismatch or a save failure clear the credentials, because presenting the old token again would be reuse.
- 401 on refresh -> credentials cleared, state `Revoked`; local refresh expiry -> `Expired` without sending anything. The reason (state name only) is kept so the "disconnected" screen survives a restart; `save()` removes it.
- Authenticated calls: one `401` -> refresh once -> repeat once (safe: the guard rejects before any handler runs); a second `401` discards the fresh token so the next call refreshes and discovers a revocation. Only `KtorDeviceHttp` may call `bearerAuth`, and no main source may log or print (both enforced by a drift test).
- Known limits: a disconnected device cannot re-pair until the parent removes the old device on the website (no self-service unenroll); refresh expiry still slides indefinitely (absolute cap = Phase 31).

## Heartbeat (Phase 12a)
- `device-heartbeat` authenticates only through `requireActiveDevice`; the device id is never read from the body (strict schema rejects it). A device revoked between the guard and the write gets the same 401.
- Two limiters: 120 / 5 min / IP **before** any crypto or database work (carrier-NAT tolerant), 8 / 15 min / device after auth. Both are in-memory per isolate until Phase 31.
- Payload is coarse (versions, battery, charging, network type); logs carry no token, id or beat data (tested). Event metadata is empty.
- Android client (12b): the beat carries only battery %, charging, network type, app and Android version — no identifiers, no location. Read with no runtime permission (sticky `ACTION_BATTERY_CHANGED`, `ConnectivityManager` under `ACCESS_NETWORK_STATE`). All requests go through `KtorDeviceHttp` (bearer token set in exactly one file; a JVM test enforces it and bans `Log.*`/`println`/hardware-identifier APIs in the heartbeat files). `HeartbeatWorker` is a WorkManager-owned class, not an exported component. A `Disconnected`/`NotEnrolled` outcome cancels the periodic work and clears the stored last-sync time.


## Device information (Phase 13a)
- `device-info` authenticates only through `requireActiveDevice`; the device id is never read from the body (strict schema rejects it, and so it rejects serial/IMEI/app-list style extra keys). A device revoked between the guard and the write gets the same 401.
- Limits: 60 / 5 min / IP before any crypto or database work, 6 / hour / device after authentication (in-memory per isolate until Phase 31). Logs contain no token, device id or uploaded value (test-enforced).
- Data minimisation: four coarse, permission-free values; parents get read-only access through the existing `devices` RLS; the upload cannot make a device look online.

## Device information — Android (Phase 13b)
- Only `KtorDeviceHttp` adds a bearer token; the upload code has none (JVM guard). No logging, no hardware-identifier, installed-app, memory-info, MAC or location API in the device-info files (`DeviceInfoContractDriftTest`). The stored report holds only the four shared values and a timestamp, sealed with the rest of the store; tampered content decodes to "nothing sent".

## Phase 14a — permission sync
`device-permissions` uses `requireActiveDevice` on every request, a strict body (device id only from the JWT), pre-auth IP limit and per-device limit. The response never reveals what changed; logs contain no states or tokens. Audit rows carry no IP.

## Phase 14b — permission sync, Android
- Only `KtorDeviceHttp` adds a bearer token; the permission-sync code has none (JVM guard). The probe only calls `checkSelfPermission`/`hasSystemFeature`: no prompt, no content API (contacts, telephony, camera, microphone, location manager, package list), no logging (`PermissionSyncContractDriftTest`). The manifest is unchanged (JVM test asserts the declared set), so the states can only read `NOT_REQUESTED`/`NOT_AVAILABLE` until a later phase declares and requests a permission.
- The request carries the eight contract keys and nothing else (no device id, package names or identifiers). The stored report and history hold only state names and key names, sealed with the rest of the store; junk or tampered content decodes to "nothing shared". A history that cannot be read can only make a state look *less* alarming (`NOT_REQUESTED`), never invent a grant.

## Phase 15a-2 — app inventory (Edge)
`device-apps` uses `requireActiveDevice` on every request, a strict body at both levels (device id only from the JWT; unknown keys such as icons or install times are rejected), a pre-auth IP limit and a per-device limit, and a 1 MiB body cap (the generic 64 KB cap would reject ordinary phones). Count (500), field lengths, package-name pattern, control characters and duplicate package names are validated at the Edge and again in SQL. The response never reveals what changed; logs and error bodies contain no tokens, package names or labels (Deno test). Parents can only read `device_apps` (RLS from 15a-1); the device is the single writer.

## Phase 15b — app inventory, Android
- `AppInventoryRepository` sanitizes the raw reading before anything is encoded (contract rules, sorted by package name, unique, at most 500; the rest is counted, never sent) and never sends an empty list (an empty reading means the read failed; it must not wipe the parent's list). A full replace is idempotent on the server, so every network failure is "try again later"; other 4xx means this run is over.
- Only `KtorDeviceHttp` adds a bearer token; the app-list code has none and no logging (`AppInventoryContractDriftTest` scans the files, bans identifier/icon/usage/signature APIs, the broad package permission and any broadcast receiver). The stored report (what the child sees) is sealed with the rest of the store; broken or tampered content decodes to "nothing sent yet". The report is cleared on enrollment, disconnect and `Stopped`.
- The fingerprint used to detect a changed list is a SHA-256 of exactly what would be sent and is never transmitted or logged.

## Phase 16a — usage statistics (Edge)
`device-usage` uses `requireActiveDevice` on every request; the device id comes only from the JWT (a body naming a device is a 400). Strict schema at both levels, hard caps on apps/minutes/counts, a bounded day window, and SQL re-validates everything (`22023`) so a bypassed Edge layer still cannot write out-of-range data. The merge is monotonic (`GREATEST`), so a replayed or re-ordered request cannot reduce stored numbers; an attacker holding a stolen device token can at most raise today's numbers within the bounds until the parent revokes the device. Logs and error bodies never contain tokens or package names (tested). Rate limits are in-memory until Phase 31.

## Phase 16b — usage statistics, Android
- **Consent and access:** `PACKAGE_USAGE_STATS` can only be enabled by the child in system settings; the app opens the settings page and never grants, prompts for or works around it. Without it nothing is read or sent. The state is read with `AppOpsManager` (no permission, no prompt) and failure reads as "unknown", never "granted".
- **Minimal data:** `AndroidUsageStatsSource` keeps five event types and only package name + timestamp; `UsageContractDriftTest` bans class names, shortcut/notification fields, extras, standby buckets, `queryUsageStats` aggregates, identifier APIs, accessibility/notification-listener services, broadcast receivers, `setMode`/`appops`/`pm grant` and any logging in the usage files, and checks that `UsageStatsManager` appears in exactly one file.
- Only `KtorDeviceHttp` adds a bearer token; usage code has none. The stored report (what the child sees) is sealed with the rest of the store; damaged or tampered content decodes to "nothing sent yet". The upload is monotonic on the server, so a replay cannot lower numbers; a stolen device token can at most raise today's numbers within the bounds until revoked (16a).


## Phase 17a — screen-time rules
`device-config` uses `requireActiveDevice` on every request; the device id comes only from the JWT, the endpoint takes no body or id parameter, the ETag is checked only **after** authentication (a 304 never reveals anything to an unauthenticated caller) and the response contains no identifiers. The parent write is a SECURITY DEFINER RPC with `search_path=''` that derives ownership from `auth.uid()` in SQL (foreign ≙ missing) and is not executable by `anon`; `daily_limit_overrides`/`config_version` have no direct grant, and `config_version` is forced by a trigger so it cannot be rolled back or pinned by a client. `SYNC_CONFIG` commands and audit rows carry no rule values (audit: field names only), so neither FCM (Phase 20) nor the audit list leaks a child's schedule. A device whose rules cannot be read (revoked between guard and read) gets the same 401 as any failed authentication. Known limitation: the `RULE_CHANGED` audit row has no IP (the RPC is called by the web server/PostgREST, not an Edge function); Phase 30 may add it.

## Phase 17b — screen-time rules (web)
Parent write path = one RPC under the caller's own session (`SECURITY DEFINER`, ownership decided in SQL; a foreign device is indistinguishable from a missing one). The web service: validates the UUID and every field before anything else; checks the user with `auth.getUser()` (Auth-server verified); rate-limits per user; has no direct table access; treats an unknown RPC response as a generic failure; logs only `rules_save_failed` + error code. The Server Action reads an allow-list of form keys, so `config_version` or a raw overrides blob cannot be injected (and the database ignores/restores them anyway). Reads are `SELECT` under RLS with an explicit column list. A structural test asserts no web file writes `device_rules` directly. Copy never promises a hard lock.

## Phase 18a — app restrictions
`device-app-events` uses `requireActiveDevice` on every request; the device id comes only from the JWT (a body naming a device is a 400). Strict schema at both levels, 1–20 events, a bounded time window (Edge narrower than SQL), and SQL re-validates everything (`22023`) so a bypassed Edge layer still cannot write bad data. The answer is only `server_time`: the device cannot learn which rules exist or which events were ignored. A stolen device token can at most add throttled `BLOCKED_APP_ATTEMPT` events for packages that are blocked right now (≤ 1 per package per 5 min, ≤ 200 per day) until the parent revokes the device. Parent writes go through `parent_set_app_rule` only (ownership in SQL, foreign ≙ missing, `22023`/`42501` mapped generically by the web layer); the cap and the "child app cannot be restricted" CHECK hold on every write path. Labels and package names never appear in logs, error bodies, audit rows (`RULE_CHANGED` carries only the field name) or the config answer's labels (tested). Rate limits are in-memory until Phase 31.

## Phase 18b — app restrictions (web)
Writes go only through RPC `parent_set_app_rule` (ownership decided in SQL, foreign ≙ missing); no web code writes `app_rules` (structural test). Server Action reads four known form keys; order UUID → field validation → verified user → rate limit (60/5 min/user, in-memory until Phase 31) → RPC. Logs: operation name + error code only (never packages, limits, ids). The minutes box is read only for `limit`; Enter in it can only set a limit. The child app cannot be restricted (contract, SQL CHECK and the UI hides the controls). Copy never promises a hard lock.

## Phase 18c — app restrictions (Android)
The device never trusts the cached rules blindly: every rule is re-validated on read (package pattern, child app excluded, limit 0–1440, blocked-or-limited, unique, ≤ 200) and an off-contract 200 is Rejected, so a damaged or tampered cache reads as "no rules". The sealed cache is codec-versioned (`v2`), so an old cache can never answer a 304 for rules it never contained. Attempts are only counted for packages blocked at check time, after the rule version was received, and after the watermark, which keeps a replayed or reordered event from inflating counts; the server independently ignores packages that are not blocked, repeats within 300 s and anything beyond 200 per device per 24 h. `AppRuleEnforcementGuardTest` fails on overlay/lock/accessibility APIs, on logging and credential headers in the rule files, and on any added permission or component. Known limit: a child can still open the blocked app (Track A cannot stop it), uninstall FamilySafe (the parent sees the device go offline) or switch Usage Access off (the child is told it is off; the parent sees the permission state).

## Phase 19a-1 — schedules (SQL)
Parent writes go through three RPCs (ownership in SQL, foreign ≙ missing) **or** the existing column grants on `schedules`; both end in the same guard trigger (cap 20, no same-type overlap, minute resolution), so no path skips validation. The guard does nothing for a device the caller does not own, so error codes (`22023`/`23P01`) cannot reveal another family's schedules — RLS answers `42501` first. The parent has no grant on `device_rules.timezone` or `schedules_revision`; the time zone is only set through the RPC (format + `pg_timezone_names`). Audit rows (`RULE_CHANGED`) carry field names only. Not run: pgTAP (`15_schedules`), concurrency of two parents editing one device (serialised by the `devices` row lock, untested).

## Phase 19a-2 — schedules on the device pull
`device-config` still authenticates with `requireActiveDevice` before anything is read; the two new keys come from the same SQL read by the device id in the JWT, so a device can only receive its own schedules and time zone. Error bodies and logs never contain schedule names, times or the zone (Deno-tested). The response schema forbids unknown keys, so no id of another device or family can be added by accident.

## Retention (Phase 32a)
`public.retention_run()` (service_role only) is the single maintenance job: it marks devices that have been silent for 45 minutes OFFLINE (a `DEVICE_OFFLINE` event, which the notification trigger turns into a parent notification) and deletes rows older than their window — audit 180 days; notifications, events, usage and location 90 days (location per-device 7/30/90 choices arrive with Phase 22a); commands 30 days; device credentials 30 days after the refresh token expired; pairing codes 7 days after they expired. It returns the number of rows changed per step and is idempotent.

**Scheduling.** The migration schedules it every 15 minutes **only when the `pg_cron` extension is already enabled** (Supabase dashboard → Database → Extensions → pg_cron); otherwise it prints a notice. It never creates the extension itself. Without a schedule nothing is purged and devices are only shown as offline by the web read-time rule. Deployment (34a) lists enabling pg_cron as a required step.

## Push wake-up (Phase 20a-3)
Parents never read or send push tokens. A parent's "refresh now" (and every rules change) creates a `SYNC_CONFIG` command; the Edge Function `commands-dispatch` hands pending commands to FCM as a **data-only wake-up `{type:"SYNC", cmd_id}`** (no notification, no rule values) and marks them pushed; a dead token is forgotten and the command stays pending. The phone never acts on a push: it pulls `device-commands`, validates the type and acknowledges. If FCM is unavailable the app still pulls on its own schedule.

**Operator steps:** set the Edge secrets `FCM_SERVICE_ACCOUNT_JSON` (Firebase service-account key, one line) and `CRON_SECRET` (≥ 32 random characters), then schedule `POST /functions/v1/commands-dispatch` every minute with the header `x-cron-secret: <CRON_SECRET>` (Supabase scheduled function, or pg_cron + pg_net). The key is never sent to the web app, the phone or a log. Rotating it = update the secret and redeploy (see the runbook in 34d).

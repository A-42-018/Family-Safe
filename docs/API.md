## Device enrollment (Phase 8 — Edge Functions, no Android code yet)
Flow: parent clicks **Add device** on `/children/[id]` → `enrollment-create` mints a pairing code → parent types it (or later scans the QR) into the Android app → `enrollment-redeem` exchanges it **once** for device credentials → parent can `device-revoke`. The gateway runs with `verify_jwt=false`; parent functions verify the Supabase JWT in-function (`requireParent`), redeem is unauthenticated by design (the single-use code is the credential). Contracts: `packages/contracts/src/enrollment.ts` (mirrored in `supabase/functions/_shared/enrollment.ts`; a test fails on drift).

| Function | Caller | Request | Success | Errors |
|---|---|---|---|---|
| `POST /functions/v1/enrollment-create` | parent JWT (called by the Next server) | `{ "child_id": uuid }` (strict) | `201 { data: { pairing_code: "XXXX-XXXX-XXXX-XXXX", qr_payload: "familysafe://enroll?c=…", expires_at, expires_in: 600 } }` | `401` bad/absent/anon token · `403` device token · `404` child missing **or not yours** · `400` validation · `429` (30/5 min/IP pre-auth, 10/15 min/parent) |
| `POST /functions/v1/enrollment-redeem` | child device, **no auth** (`Authorization` is never read) | `{ code, device_name (1–100), manufacturer?, model?, android_version?, app_version? }` (strict: no `child_id`/status/ids accepted) | `201 { data: { device_id, token_type: "Bearer", access_token (HS256 device JWT, 15 min, claims sub=device_id, cid=credential id, jti), access_expires_in: 900, refresh_token (256-bit opaque), refresh_expires_at (+30 d) } }` | `401 "Invalid or expired pairing code"` for unknown, expired **and** already-used codes (identical body) · `400` validation · `429` (5 attempts / 5 min / IP, every attempt counts) |
| `POST /functions/v1/device-revoke` | parent JWT | `{ "device_id": uuid }` (strict) | `200 { data: { revoked: true, already_revoked: bool } }` (idempotent) | `401/403/400/429` as above · `404` device missing or not yours · (20 / 5 min / parent) |

Pairing code: 16 Crockford-base32 symbols (80 bits, CSPRNG, unbiased), typed as `XXXX-XXXX-XXXX-XXXX`; input is case-insensitive and accepts `O→0`, `I/L→1`, spaces and hyphens. TTL 10 min, one live code per child (minting again replaces the previous unconsumed one). Only `HMAC-SHA256(PAIRING_TOKEN_PEPPER, code)` is stored. QR payload = `familysafe://enroll?c=<code>`; the app gets its API base URL from its build config (Phase 9/10). The Android app (Phase 10) types/pastes the code (a pasted QR payload is unwrapped), sends only `code`, `device_name`, `manufacturer`, `model`, `android_version`, `app_version` to `enrollment-redeem` with no `Authorization` header, keeps only `device_id` + `refresh_token` + its expiry (the 15-minute access token is dropped until Phase 11), and maps 401 → "invalid or expired", 429 → "too many tries" (`Retry-After` seconds if present), 5xx → "try again", other 4xx → "update the app".
Redeem result: device row `ENROLLED` (rules all OFF, permissions NOT_REQUESTED via trigger), one live refresh credential (SHA-256 stored), audit row `DEVICE_ENROLLED` for the parent who minted the code (no IP stored). FCM token registration and first heartbeat come in Phases 10/12/20; refresh-token rotation and `cid` revocation checks in Phase 11.
Revoke: device `REVOKED`/`OFFLINE`, every credential `revoked_at` set, push registration deleted, audit `DEVICE_REMOVED` (`metadata.reason="revoked"`, parent IP). The device row and history remain; hard removal belongs to Phase 32. To re-enroll a phone, add it as a new device.

Web (Server Actions in `apps/web/lib/enrollment/actions.ts`, POST-only): `createPairingCodeAction(childId)` and `revokeDeviceAction(id, confirm="revoke")` forward the parent's own access token from the server-side session to the functions; the browser never sees a token. UI on `/children/[id]`: **Add device** dialog (shows the code once, drops it from client state when closed), device list with status badge, last seen and **Revoke access**.

## Device authentication (Phase 11 — Edge Function + shared guard + Android client)
| Endpoint | Auth | Request | Success | Errors |
|---|---|---|---|---|
| `POST /functions/v1/device-refresh` | child device, **no header auth** (`Authorization` is never read; the 256-bit refresh token is the credential) | `{ refresh_token }` — exactly 43 base64url chars, strict (no device id / cid / status accepted) | `200 { data: { device_id, token_type: "Bearer", access_token (HS256, 15 min, sub=device_id, cid=**new** credential id, jti), access_expires_in: 900, refresh_token (**new**, 256-bit), refresh_expires_at (+30 d, sliding) } }` | `401 "Invalid or expired refresh token"` for unknown, expired, revoked, replayed **and** revoked-device tokens (identical body) · `400` validation · `429` (60 / 5 min / IP, every attempt counts, `Retry-After`) · sanitized `500` |

**Rotation.** Every successful refresh invalidates the presented token and returns a new one in the same `token_family_id`; the client must persist the new refresh token **before** using the new access token. **Reuse detection:** presenting a token that was already rotated (stolen, or the response to the last refresh was lost) revokes the whole family, sets the device `REVOKED`/`OFFLINE`, drops its push registration and writes a `DEVICE_REMOVED` audit row (`reason: credential_reuse`) for the owning parent — the parent must add the device again. The client cannot tell this apart from any other 401, by design; a lost response is therefore handled as "credentials unknown → re-enroll", never by retrying the old token.

**Guard for every later device endpoint.** `requireActiveDevice(req, { secret, isActive })` in `_shared/auth.ts` verifies the JWT (HS256 only, exp/iat, `role=device`), requires a `cid` claim, and calls `device_authorize(device_id, cid)` on **every request** (uncached). A revoked device is refused on its very next call although its access token is still unexpired; this closes the Phase 8 "valid ≤ 15 min after revoke" gap. Any rejection is the same `401`; a lookup failure is a sanitized `500` (never "valid"). Contract: `packages/contracts/src/device-auth.ts` (mirrored in `supabase/functions/_shared/device-auth.ts`; a test fails on drift). Endpoints for heartbeat, config, commands etc. (Phase 12+) must use this guard.

**Android client (Phase 11b).** `KtorRefreshApi` posts `{ refresh_token }` with no credential header and never retries. Status handling (`RefreshHttpMapper`): `200` -> new tokens; `401` -> credentials rejected (cleared); `429` -> keep token, honour `Retry-After` delta-seconds; `502`/`503` -> gateway did not run the function, keep token; **any other 5xx and any unusable `200` -> uncertain** (our own sanitized `500` can follow a committed rotation); other `4xx`/`3xx` -> nothing rotated, keep token. Network errors: only failures that prove the request never left the device (DNS, refused, TLS handshake, connect timeout) may retry the same token; everything else is uncertain. Device endpoints are called through `KtorDeviceHttp` -> `AuthenticatedExecutor` (`Authorization: Bearer`; on one `401` refresh once and repeat once).

## Heartbeat (Phase 12a — Edge Function; Phase 12b — Android client)
| Endpoint | Auth | Request | Success | Errors |
|---|---|---|---|---|
| `POST /functions/v1/device-heartbeat` | device access JWT via `requireActiveDevice` (live credential check on every request) | `{ app_version (1–32), android_version (1–32), battery_level (int 0–100), is_charging (bool), network_type (WIFI\|CELLULAR\|ETHERNET\|VPN\|NONE\|UNKNOWN) }` — strict: no device id, location, app names or permission state | `200 { data: { server_time, next_interval_seconds: 900 } }` | `401` (missing/forged/expired/parent token, revoked or unknown credential, or device revoked mid-request — identical body) · `400` validation · `429` (120 / 5 min / IP before auth, 8 / 15 min / device after auth, `Retry-After`) · sanitized `500` |

The device id is taken from the verified token. `device_heartbeat` (SQL, one transaction, row-locked) overwrites `app_version`, `android_version`, `battery_level`, `is_charging`, `network_type`, sets `last_seen_at = now()` and `device_status = ONLINE`, and writes `DEVICE_ONLINE` only on a transition into ONLINE and `BATTERY_LOW` only when the device newly becomes low (level ≤ 15 and not charging). **Offline rule:** a device whose `last_seen_at` is older than 2700 s (3 missed beats) is *shown* as offline at read time (web, Phase 12c) and can be *swept* with `device_mark_stale_offline(p_stale_seconds)` (writes `DEVICE_OFFLINE`); scheduling the sweep is decided in Phase 31/34. Permission state and the client-side "last sync" are not in the beat: permission sync is Phase 14, and `last_seen_at` is the server-side truth.

**Android client (Phase 12b).** `HeartbeatWorker` (WorkManager unique periodic work `heartbeat`, 15 min, network `CONNECTED`, exponential backoff from 1 min) calls `HeartbeatRunner` → `HeartbeatRepository` → `KtorDeviceHttp` (the only place a bearer token is set; one `401` → refresh once → repeat once). Outcome mapping: `2xx` → recorded (last sync = `server_time`, falling back to the local clock if the body is unreadable) · `401` after the refresh, `429`, any `5xx`, offline, or a `Retry` from the token provider → `Result.retry()` (safe: the beat is an idempotent overwrite) · other `4xx`/`3xx` → `Result.failure()` for this run only (periodic work continues next period) · no credentials / disconnected → periodic work cancelled, "last sync" cleared. The first authenticated call rotates the refresh token and moves the auth state to `Connected`.

## Heartbeat display (Phase 12c — web, no new endpoint)
No Edge Function, migration or contract change. The parent web app reads `devices` (heartbeat columns `device_status`, `last_seen_at`, `battery_level`, `is_charging`, `network_type`, `app_version`, `android_version`, plus `children(name)`) through Server Components under RLS; foreign and missing device ids both answer 404. Display rule: **online = `device_status = 'ONLINE'` and `last_seen_at` within 2700 s** (`HEARTBEAT_STALE_SECONDS`), evaluated at request time so a silent device shows offline before any sweep. Pages refresh via `router.refresh()` every 60 s while the tab is visible.

The device id is taken from the verified token. `device_update_info` (SQL, row-locked) overwrites `sdk_level`, `security_patch`, `storage_total_mb`, `storage_free_mb` and sets `info_updated_at = now()`. It **never** changes `device_status` or `last_seen_at` (only the heartbeat is the liveness signal) and writes no device events. `manufacturer`, `model`, `android_version` and `app_version` already exist (enrollment + heartbeat) and are not part of this upload.

**Android client (13b):** sends all four keys every time (unknown = explicit `null`), once a day and after an OS/patch update; a patch date after today (UTC) is sent as `null` (stricter than the server's one-day slack). A `400` ends that run without retry.

**Web display (13c):** no new endpoint. The overview page reads `sdk_level`, `security_patch`, `storage_total_mb`, `storage_free_mb`, `info_updated_at` through `DEVICE_COLUMNS` under RLS (read-only for parents) and renders them via `lib/devices/info.ts`.

**Android client (14b):** sends all eight keys every time (state names exactly as in the contract), every 6 hours and when the app resumes with a changed, unacknowledged or ≥ 30-minute-old state (unique one-time job, never more than one pending). A `400` ends that run without retry. The app reads the OS state without prompting; SMS and call log are always `NOT_AVAILABLE` in this distribution.

**Web display (Phase 14c):** no new endpoint. `/devices/[id]/permissions` reads `device_permissions` (8 `*_status` columns + `last_verified_at`) through the parent's own session under RLS (`SELECT` granted to `authenticated`, scoped by `owns_device`; covered by the `05_rls` isolation test and the no-write test). Values are the device's report, not proof.

**App inventory (Phase 15a-2):** order = method → IP limit → `requireActiveDevice` → per-device limit → strict body → `device_sync_apps` → `{ server_time, next_interval_seconds }`. The device id comes from the verified token only. `device_sync_apps` (15a-1) replaces the stored list in one transaction (missing rows deleted, new inserted, changed updated), sets `devices.apps_synced_at`, writes `APP_INSTALLED`/`APP_UNINSTALLED` events only after the first (baseline) report, never touches `device_status`/`last_seen_at`, and writes no audit row. **Android client (Phase 15b):** the app posts the sanitized launcher-app list to `device-apps` once a day and after a change (status mapping: `2xx` recorded; `401` after the single refresh, `429`, `5xx`, network errors retry; other `4xx` ends the run; never an empty list; max 500 apps, the rest counted locally). `Retry-After` is parsed but WorkManager backoff is used.

**Web display (Phase 15c):** no new endpoint. `/devices/[id]/applications` reads `devices.apps_synced_at` and `device_apps` (`package_name`, `label`, `version_name`, `is_system`; at most `DEVICE_APPS_MAX` rows) through the parent's own session under RLS (`SELECT` only, scoped by `owns_device`; covered by the `11_device_apps` pgTAP isolation and no-write tests). URL parameters: `q` (search text, ≤ 100 characters) and `kind` (`all` \| `user` \| `system`; anything else = `all`). Values are the device's report, not proof.

## 15. Usage statistics (Phase 16a, Edge + contracts)
`POST /functions/v1/device-usage` (device JWT, `requireActiveDevice`; body `{day:"YYYY-MM-DD", total_screen_minutes, unlock_count, apps:[{package_name, foreground_minutes, launch_count}]}`, strict at both levels, no device id). Day window today-14 … today+1 (UTC); minutes 0–1440; counts 0–10000; ≤ 200 apps; no duplicate packages; app minutes sum ≤ 1440. Values are cumulative per day; the server keeps the larger value per column (never lowers, never deletes). `200 {server_time, next_interval_seconds: 21600}`; inactive/revoked → the usual uniform `401`; `429` per IP (60/5 min) and per device (12/h). Contracts: `packages/contracts/src/device-usage.ts` (+ Edge mirror `_shared/device-usage.ts`, drift-tested against the mirror, the migration and `index.ts`).

### Android client (Phase 16b)
The child app calls `POST device-usage` through `DeviceHttp` (bearer added only in `KtorDeviceHttp`). Body = the strict contract above, built after sanitizing: day = child's local date; at most 200 apps ranked by minutes, app minutes summing to ≤ 1440, unique valid package names, apps with neither minutes nor launches dropped. Outcomes: `2xx` → recorded; `401` (after the executor's one refresh), `429`, any `5xx`, network error → retry later (monotonic merge makes repeats harmless); other `4xx` → this run fails. Cadence: every 6 h, on app resume when due (≥ 30 min since the last acknowledged upload), once more for yesterday on the first upload of a new local day. Nothing is sent while Usage Access is off.

**Web display (Phase 16c-1):** no new endpoint. `/devices/[id]/usage` reads `devices.usage_synced_at`, `device_usage_daily` (`usage_date`, `total_screen_minutes`, `unlock_count`; at most 9 rows), `app_usage_daily` (`package_name`, `foreground_minutes`, `launch_count`; at most `DEVICE_USAGE_MAX_APPS` rows for one day) and, for the top 10 apps, `device_apps.label`, all through the parent's own session under RLS (`SELECT` only, scoped by `owns_device`). URL parameter: `day` (`YYYY-MM-DD`; anything else = latest day). Values are the device's report, not proof.

**Web display (Phase 16c-2):** no new endpoint. `/dashboard` additionally reads, through the parent's own session under RLS (`SELECT` only), `devices.usage_synced_at` (enrolled devices) and `device_usage_daily` (`device_id`, `usage_date`, `total_screen_minutes`, `unlock_count`; UTC yesterday … +1 day; at most 3 rows per device). Values are the devices' reports, not proof.


## 16. Screen-time rules / device config (Phase 17a, Edge + RPC + contracts)
**Device pull — `GET /functions/v1/device-config`** (device JWT, `requireActiveDevice`; no body, nothing in the request can name a device). 200 `{data:{config_version, daily_limit_minutes|null, daily_limit_overrides:{"1".."7":0..1440}, bedtime_enabled, bedtime_start|null, bedtime_end|null ("HH:MM", null unless bedtime is enabled), school_mode_enabled, server_time, next_interval_seconds:21600}}` with `ETag: "v<config_version>"`. A matching `If-None-Match` (`"v3"` or `W/"v3"`; lists, `*` and junk are ignored) gets **304 with no body** — still after the device check. Effective limit for an ISO weekday = override if present (0 = no screen time that day) else the default; `null` default + no override = no limit (`effectiveDailyLimitMinutes` in contracts). Only GET (others 400); limits 60/5 min/IP pre-auth and 30/h/device; revoked/unknown/inactive = the usual identical 401. Read-only: never touches `device_status`/`last_seen_at`.

**Parent write — RPC `parent_set_screen_time_rules(p_device_id, p_daily_limit_minutes, p_daily_limit_overrides)`** (PostgREST `rpc`, caller's own session; no Edge function). Returns one row `{o_outcome, o_config_version}`: `updated` | `unchanged` (identical input: no write/bump/command/audit) | `not_found` (foreign ≙ missing) | `inactive` (own REVOKED/PENDING device: read-only). Invalid input = SQLSTATE `22023`, no session = `42501`. Contract for the 17b form: `screenTimeRulesInputSchema`.

**Change signalling:** every real change of the config columns (whatever the write path) bumps `device_rules.config_version` by 1, queues one `SYNC_CONFIG` command (payload `{}`, 24 h, only for ENROLLED devices, deduped while one is PENDING) and — when made by the owning parent — writes a `RULE_CHANGED` audit row with field **names** only. The command never carries rule values; the device pulls. Until Phase 20 (FCM + command pull) the device relies on its periodic pull (`next_interval_seconds`).

**Web (Phase 17b):** no new endpoint. `/devices/[id]/rules` reads `device_rules` (`config_version`, `daily_screen_limit_minutes`, `daily_limit_overrides`, `bedtime_enabled`, `bedtime_start`, `bedtime_end`, `school_mode_enabled`, `updated_at`) and writes **only** through RPC `parent_set_screen_time_rules` from the Server Action `saveScreenTimeRulesAction`, both under the parent's own session. Form keys (everything else is ignored): `device_id`, `default_mode` (`off|limit|zero`), `default_minutes`, `mode_1…7` (`default|limit|zero`), `minutes_1…7` (whole minutes 1–1440, read only when the mode is `limit`). Rate limit `DEVICE_RULES.write` 30/5 min per user (in-memory until Phase 31). `/dashboard` additionally reads `device_rules` for enrolled devices (`SELECT` only, at most one row per device).

## 17. App restrictions (Phase 18a — Edge + RPC + contracts; web = 18b, Android = 18c)
**Parent write — RPC `parent_set_app_rule(device, package, blocked, daily_limit_minutes|null)`** (PostgREST `rpc` under the parent's own session; `authenticated` only; no Edge function). Returns `(o_outcome, o_config_version)` with outcomes `updated | cleared | unchanged | not_found | inactive | unknown_app` (`APP_RULE_OUTCOMES`). `not_found` covers a missing and a foreign device alike; `inactive` = own device that is revoked/pending (rules are read-only); `unknown_app` = a *new* rule for a package the device has not reported in its app inventory. `blocked = false` with no limit means "no restriction": an existing rule is deleted (`cleared`), otherwise `unchanged`. Invalid input (package format, the child app `app.familysafe.child`, limit outside 0–1440, null flag) raises `22023`; no session raises `42501`; more than `APP_RULES_MAX = 200` rules per device raises `22023`. Input contract for 18b: `appRuleInputSchema`.

**Device pull — `GET device-config`** now also returns `app_rules: [{package_name, blocked, daily_limit_minutes|null}]` (ordered by package name, ≤ 200, only rows that restrict something, **never a label**). `blocked` wins over a stored limit. A change of the effective rules bumps `config_version` (so the ETag/304 logic of 17a covers app rules too) and queues one `SYNC_CONFIG` command. Contract: `appRuleSchema`, `deviceConfigSchema.app_rules` (unique packages).

**Device event — `POST /functions/v1/device-app-events`** (device JWT, `requireActiveDevice`; body `{events:[{type:"BLOCKED_APP_ATTEMPT", package_name, occurred_at}]}`, strict at both levels, 1–20 events, no device id, no label). `occurred_at` = UTC `YYYY-MM-DDTHH:MM:SS[.f{1,9}]Z` only, real calendar date, not older than 24 h and not more than 5 min ahead (the Edge accepts a window 60 s narrower on both sides, so the database never rejects what the Edge accepted). `200 {server_time}` — the answer never says what was stored or ignored. The database stores an event only for a package that is **blocked right now**, at most one per package per 5 minutes, at most 200 per device per 24 h; everything else is silently ignored. Inactive/revoked → the usual identical `401`; `429` per IP (60/5 min, pre-auth) and per device (30/h). Never touches `device_status`/`last_seen_at`, writes no audit row, queues no command. Contracts: `packages/contracts/src/device-app-events.ts` (+ Edge mirror `_shared/device-app-events.ts`, drift-tested against the mirror, the migration and `index.ts`).

### Web app restrictions (Phase 18b)
No new endpoint. `/devices/[id]/applications` reads `app_rules` (`package_name,blocked,daily_limit_minutes`, ≤ `APP_RULES_MAX`, SELECT only) and writes **only** through RPC `parent_set_app_rule` from the Server Action `saveAppRuleAction`, under the parent's own session. Form keys (everything else is ignored): `device_id`, `package_name`, `intent` (`block|limit|clear`), `minutes` (whole minutes 1–1440, read only for `limit`). RPC outcomes `updated | cleared | unchanged | not_found | inactive | unknown_app` are mapped generically; logs carry only `app_rule_save_failed` + the error code. Rate limit `APP_RULES.write` 60/5 min per user (in-memory until Phase 31). `/dashboard` additionally reads `app_rules` (`device_id` + the three columns) for enrolled devices.

### Android app-rule check and attempt upload (Phase 18c)
No new endpoint. The device already pulls `app_rules` with `GET device-config` (sealed cache **codec v2**: `v2;validatedAt;version;limit;overrides;bedtime;school;apps`; the pre-18c six-field cache reads as "no cache" so the next pull is a full one — the ETag now covers app rules). A missing or `null` `app_rules` key in a 200 body is **Rejected** (never read as "no restrictions"). Blocked apps that were opened are sent with `POST device-app-events` (`{events:[{type:"BLOCKED_APP_ATTEMPT", package_name, occurred_at}]}`, 1–20 events, UTC whole seconds). The app keeps a small sealed outbox (≤ 40, oldest dropped first), de-duplicates the same package within 300 s (the server does the same), drops attempts older than the narrowed server window, and uses the standard outcome mapping: 2xx sent, 401/429/5xx/network → retry (repeats are harmless), other 4xx → that batch is dropped. Only packages blocked **right now** produce events; limits are never reported.

## 18. Schedules (Phase 19a-1 SQL + 19a-2 Edge/contracts)
**Parent write — RPCs** (PostgREST `rpc` under the parent's own session; `authenticated` only; no Edge function): `parent_save_schedule(device, schedule|null, name, type, days[], 'HH:MM', 'HH:MM', enabled)` → `{o_outcome: created|updated|unchanged|overlap|limit_reached|not_found|inactive, o_schedule_id, o_config_version}`; `parent_delete_schedule(device, schedule)` → `{deleted|not_found|inactive, o_config_version}`; `parent_set_device_timezone(device, tz|null)` → `{updated|unchanged|not_found|inactive, o_config_version}`. `22023` invalid input (also: unknown time zone), `42501` no session. Web (19b) must map outcomes generically (no ids/values in logs).
**Device pull — `GET device-config`** (19a-2): the response `data` now also carries `timezone` (IANA name, or `null` = the device's own zone) and `schedules` (ENABLED windows only, ordered by type, start, id, ≤ 20; each `{id, name, type: BEDTIME|SCHOOL|CUSTOM, days: [1..7 ascending], start_time: "HH:MM", end_time: "HH:MM"}`; `end_time < start_time` = overnight, belongs to the day it starts on, Sunday wraps into Monday). Both keys are always present (`null` / `[]`, never absent). The ETag/304 behaviour is unchanged: a schedule or time-zone change bumps `config_version`, so the old ETag gets the full body. Contracts: `scheduleSchema`, `timezoneSchema`, `SCHEDULES_MAX = 20`, parent inputs `scheduleInputSchema` / `scheduleDeleteInputSchema` / `timezoneInputSchema` (for 19b), outcome lists `SCHEDULE_SAVE_OUTCOMES` / `SCHEDULE_DELETE_OUTCOMES` / `TIMEZONE_OUTCOMES`, helpers `scheduleWeekRanges` / `schedulesOverlap` (mirror SQL `schedule_week_ranges`). `deviceConfigSchema` rejects duplicate ids and same-type overlaps. The shipped Android 18c parser ignores the new keys (`ignoreUnknownKeys`); Phase 19c reads them.
